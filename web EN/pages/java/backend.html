1. SQL & Database

ACID Properties

Atomicity

Toàn bộ hoặc không gì cả. Transaction commit → all changes. Rollback → không thay đổi nào.

Consistency

Dữ liệu từ trạng thái hợp lệ này sang hợp lệ khác. Ràng buộc (FK, unique, check) luôn được đảm bảo.

Isolation

Transaction không ảnh hưởng lẫn nhau. Các mức: READ_UNCOMMITTED, READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE.

Durability

Dữ liệu đã commit được lưu vĩnh viễn. Dùng WAL (Write-Ahead Log) để phục hồi khi crash.

Index chi tiết

-- B-Tree index (mặc định) — tốt cho =, >, <, BETWEEN, LIKE 'abc%'
CREATE INDEX idx_email ON users(email);

-- Composite index — áp dụng left-most prefix
CREATE INDEX idx_name_age ON users(last_name, first_name, age);
-- Dùng được: WHERE last_name='Nguyen'
-- Dùng được: WHERE last_name='Nguyen' AND first_name='An'
-- KHÔNG dùng được: WHERE first_name='An'  (thiếu last_name)
-- Dùng được 1 phần: WHERE last_name='Nguyen' AND age=25  (chỉ index last_name)

-- Unique index
CREATE UNIQUE INDEX idx_email_unique ON users(email);

-- Partial index (PostgreSQL) — chỉ index dòng thỏa điều kiện
CREATE INDEX idx_active_users ON users(email) WHERE status = 'ACTIVE';

-- Covering index — index chứa sẵn data, không cần truy cập table
CREATE INDEX idx_covering ON users(email) INCLUDE (name, avatar_url);

-- Giải thích query plan
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'test@email.com';

Transaction & Locking

-- Pessimistic Lock — khóa dòng khi đọc, tránh concurrent update
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT o FROM Order o WHERE o.id = :id")
Optional<Order> findByIdForUpdate(@Param("id") Long id);

-- Optimistic Lock — dùng version column, throw exception khi conflict
@Entity
public class Product {
    @Version
    private Long version;
}
// Khi update, Hibernate: UPDATE product SET ... WHERE id=? AND version=oldVersion
// Nếu version thay đổi → OptimisticLockException → retry

-- Deadlock — 2 transaction lock nhau
-- Transaction 1: UPDATE accounts SET balance=balance-100 WHERE id=1;
--               UPDATE accounts SET balance=balance+100 WHERE id=2;
-- Transaction 2: UPDATE accounts SET balance=balance-200 WHERE id=2;
--               UPDATE accounts SET balance=balance+200 WHERE id=1;
-- Fix: luôn lock theo cùng thứ tự (id 1 → 2)

Query Optimization

  • EXPLAIN ANALYZE: xem seq scan vs index scan, các bước, thời gian
  • N+1: dùng JOIN FETCH, @EntityGraph, batch fetching
  • Chỉ SELECT cần thiết: không SELECT * — chỉ lấy cột cần
  • Pagination: keyset pagination (WHERE id > lastId) thay vì OFFSET
  • Connection pool: HikariCP size ~ 2*CPU + 1, không lớn quá
  • Avoid lock trong transaction: transaction càng ngắn càng tốt
2. NoSQL Databases

Redis

In-memory key-value. Dùng: cache, session, rate limiter, distributed lock, pub/sub. Data structures: String, List, Set, Sorted Set, Hash, Bitmap, HyperLogLog.

MongoDB

Document DB (JSON-like). Dùng: flexible schema, nested data, fast prototyping. Query: find, aggregate pipeline. Index: single, compound, text, geospatial.

Cassandra

Wide-column, write-optimized. Dùng: time-series, IoT, event logging. Partition key + clustering key. CQL (Cassandra Query Language).

Elasticsearch

Full-text search + analytics. Dùng: logging (ELK), search engine, product search. Inverted index, aggregation, scoring.

Redis Patterns

// Cache Aside
public User getUser(Long id) {
    String key = "user:" + id;
    String cached = redis.opsForValue().get(key);
    if (cached != null) return deserialize(cached);     // cache hit
    User user = userRepo.findById(id).orElse(null);     // miss → get from DB
    if (user != null) redis.opsForValue().set(key, serialize(user), 1, TimeUnit.HOURS);
    return user;
}

3. Message Queue (Kafka & RabbitMQ)

🐇 RabbitMQ

Message broker cổ điển. Exchange types: Direct, Topic, Fanout, Headers. Dùng cho: task queue, RPC, pub/sub. Guarantee delivery (consumer ack).

📊 Kafka

Distributed event streaming. Topic, Partition, Consumer Group, Offset. Dùng cho: event sourcing, stream processing, CDC, log aggregation. Lưu message trên disk.

Spring Kafka

// Producer
@RestController
public class OrderController {
    @Autowired private KafkaTemplate<String, OrderEvent> kafka;

    @PostMapping("/orders")
    public Order create(@RequestBody @Valid CreateOrderRequest req) {
        Order order = orderService.create(req);
        kafka.send("order-events", new OrderEvent(order.getId(), "CREATED"));
        return order;
    }
}

// Consumer
@Component
public class OrderEventHandler {

    @KafkaListener(topics = "order-events", groupId = "notification-service")
    public void handleOrderCreated(OrderEvent event) {
        // Xử lý: gửi email, push notification, cập nhật inventory
        if (event.getType().equals("CREATED")) {
            emailService.sendOrderConfirmation(event.getOrderId());
        }
    }

    @KafkaListener(topics = "order-events", groupId = "analytics-service")
    public void handleForAnalytics(OrderEvent event) {
        analyticsService.recordEvent(event);
    }
}

// Kafka Configuration
@Configuration
public class KafkaConfig {
    @Bean
    public ConsumerFactory<String, OrderEvent> consumerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ConsumerConfig.GROUP_ID_CONFIG, "order-group");
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, JsonDeserializer.class);
        props.put(JsonDeserializer.TRUSTED_PACKAGES, "com.example.event");
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);  // manual commit
        return new DefaultKafkaConsumerFactory<>(props);
    }
}

Kafka Streams (xử lý real-time)

// Đếm số đơn hàng mỗi phút
StreamsBuilder builder = new StreamsBuilder();

KTable<Long, Long> countPerMinute = stream

    .groupBy((k, v) -> v.getProductId())

    needs: test
    steps:
      - uses: actions/checkout@v4

      - run: |

CAP Theorem

(Banking) (Single-node)

Partition --- Availability
AP (Social media, CDN)

Trong distributed system, khi có network partition (P), bạn chỉ chọn được C (consistency) hoặc A (availability). Không có hệ thống nào có cả 3 cùng lúc.

Common Design Questions

URL Shortener

Base62 encoding (7 ký tự = 3.5T URLs). Redis cache hot URLs. DB sharding. 301 redirect.

Rate Limiter

Token Bucket + Redis Lua script. Per user/IP/API. Headers: X-RateLimit-Remaining, Retry-After.

Chat System

WebSocket Gateway cluster. Kafka cho message queue. Cassandra cho message storage. Redis pub/sub cho presence.

Notification System

Kafka topic → Push Worker (FCM/APNs), Email Worker (SES), SMS Worker (Twilio). Rate limiting + DLQ.

Estimation Cheat Sheet

1 request/second = 86,400 requests/day ≈ 2.5M/month
1M requests/day ≈ 12 requests/second
1GB/s = ~8Gbps bandwidth
PostgreSQL: ~5k writes/s, ~50k reads/s (single node)
Redis: ~100k ops/s (single node)
Kafka: ~1M messages/s (cluster)
Network latency: data center 0.5ms, same region 5ms, cross-continent 100-200ms
avg DB query: 5-50ms (with index), 100-500ms (full scan)
8. Performance Optimization

Caching Layers

Client → CDN (CloudFront) → Reverse Proxy (Nginx) → App Cache (Caffeine) → Distributed Cache (Redis) → Database

Database Optimization

  • Index tối ưu: composite index cho query thường xuyên, partial index cho filtered query
  • Connection pool: HikariCP size = 2*CPU+1, monitor active/pending connections
  • Read replicas: PostgreSQL primary for write, replicas for read. Spring @Transactional(readOnly=true) → replica
  • Query optimization: EXPLAIN ANALYZE, tránh full scan, LIMIT + OFFSET → keyset pagination

Application Optimization

9. Architecture Patterns

Monolithic

1 ứng dụng, 1 DB. Đơn giản, dễ develop. Giới hạn: scaling, team size. Phù hợp: startup, MVP.

Microservices

Nhiều service nhỏ, độc lập. Deploy riêng, team riêng. Cần: API Gateway, service discovery, distributed tracing, orchestrator.

CQRS + Event Sourcing

Tách read/write model. Lưu events thay vì state. Dùng cho: audit, complex business rules, temporal queries.

Event-Driven

Service giao tiếp qua events (Kafka). Decouple, scalable. Saga pattern cho distributed transaction. Outbox pattern cho reliable publishing.

Outbox Pattern

// Vấn đề: ghi DB + publish Kafka — 2 hành động không atomic
// Outbox: ghi event vào DB cùng transaction, CDC capture và publish

@Entity
@Table(name = "outbox")
public class OutboxEvent {
    @Id @GeneratedValue
    private Long id;
    private String aggregateType;   // "order"
    private String aggregateId;     // "123"
    private String eventType;       // "OrderCreated"
    private String payload;         // JSON
    private LocalDateTime createdAt;
}

// Service — atomic với DB transaction
@Transactional
public Order createOrder(CreateOrderRequest req) {
    Order order = orderRepo.save(toEntity(req));
    outboxRepo.save(new OutboxEvent("order", order.getId(), "OrderCreated", serialize(req)));
    return order;
}

// CDC Worker — Debezium (Kafka Connect) capture changes từ outbox → publish lên Kafka
