1. Monitoring vs Observability

Monitoring là gì?

The process of collecting and analyzing metrics/logs to detect known problems and trigger alerts. (Thu thập và phân tích metrics/logs để phát hiện vấn đề đã biết và bắn cảnh báo.)

Observability là gì?

The ability to understand the internal state of a system from its external outputs (metrics, logs, traces) — cho phép hỏi "tại sao" và debug cả những vấn đề chưa từng gặp. (Khả năng hiểu trạng thái bên trong hệ thống từ đầu ra bên ngoài — hỏi "tại sao" và debug cả vấn đề mới.)

📋 Monitoring

Trả lời "có gì sai không?" — check theo threshold đã biết trước.

🔍 Observability

Trả lời "tại sao sai?" — khám phá không giới hạn câu hỏi đã định.

Tại sao quan trọng?

  • Phát hiện sự cố sớm (trước khi user báo).
  • Debug nhanh qua logs/traces thay vì đoán mò.
  • Đo lường SLO/SLA — cơ sở cho quyết định release.
2. Ba trụ cột (The Three Pillars)

📈 Metrics Số liệu

Giá trị số theo thời gian: CPU, RAM, latency, error rate, request count. Rẻ, lưu lâu, dễ vẽ biểu đồ. VD: Prometheus, CloudWatch.

📜 Logs Nhật ký

Sự kiện chi tiết dạng text: error stacktrace, request log. Giàu thông tin nhưng đắt, cần indexing. VD: ELK, Loki, CloudWatch Logs.

🔗 Traces Vết

Hành trình của 1 request xuyên qua nhiều services — span + trace ID. Quan trọng cho microservices. VD: Jaeger, Zipkin, X-Ray.

User → Gateway (span) → Order Service (span) → Payment Service (span) → DB (span)
[trace: toàn bộ hành trình — gồm nhiều spans, chia sẻ trace_id]

Ví dụ trace

# Trace ID gắn xuyên suốt request
GET /api/orders/123
  ├─ span: auth-service  (12ms)
  ├─ span: order-service (45ms)
  │    └─ span: redis-cache (3ms)
  └─ span: payment-service (120ms)   ← bottleneck phát hiện tại đây
3. Golden Signals (Tín hiệu vàng)

4 tín hiệu chính của Google SRE

🕐 Latency

Thời gian phản hồi request. Đo cả phân phối (p50, p95, p99) — không chỉ trung bình.

📦 Traffic

Lượng yêu cầu hệ thống phục vụ (RPS, requests/second).

❌ Errors

Rate lỗi — HTTP 5xx, exceptions, responses sai (kể cả 200 nhưng nội dung lỗi).

🚦 Saturation

Mức độ "đầy" của hệ thống — CPU, memory, queue depth. Dấu hiệu trước khi quá tải.

Ví dụ (Example)

# Phân phối latency — p95 quan trọng hơn average
Latency p50 = 80ms    ← nửa số request nhanh hơn 80ms
Latency p95 = 450ms   ← 5% request chậm hơn 450ms (cần xem)
Latency p99 = 1.2s    ← user hiếm gặp phải 1.2s

# Error rate
Error Rate = (5xx + business errors) / total requests  →  target < 1%
4. Prometheus

Prometheus là gì?

Open-source monitoring & alerting toolkit — thu thập metrics qua HTTP pull model, lưu trong time-series DB, query bằng PromQL. (Open-source monitoring toolkit — scrapes metrics via HTTP pull model, stores in a time-series DB, queries with PromQL.)

App (exposes /metrics) ◀── scrape (pull) ─── Prometheus Server ──▶ Grafana (visualize)
                                                           └── Alertmanager (alerts)

Metric types

Counter

Chỉ tăng: request count, error count. Reset khi restart.

Gauge

Tăng/giảm được: CPU usage, memory, temperature.

Histogram

Đo phân phối: latency (buckets) — tính được p95/p99.

Summary

Tương tự histogram nhưng tính percentiles phía client.

Ví dụ metrics + PromQL (Example)

# App expose /metrics (Spring Boot + Micrometer)
# http_server_requests_seconds_count{uri="/api/orders",status="200"} 1280

# PromQL — request rate
rate(http_server_requests_seconds_count[5m])

# Error rate %
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
  / sum(rate(http_server_requests_seconds_count[5m])) * 100

# p95 latency
histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket[5m])) by (le))
5. Grafana

Grafana là gì?

Open-source dashboard/visualization platform — nguồn dữ liệu từ Prometheus, Loki, CloudWatch, Elasticsearch... (Open-source dashboard platform — pulls from Prometheus, Loki, CloudWatch, Elasticsearch, and more.)

Thành phần chính

  • Dashboards: biểu đồ (graph, gauge, heatmap) theo panels.
  • Alerting: rule dựa trên query → gửi notification (Slack, Email, PagerDuty).
  • Data sources: kết nối nhiều backend metrics/logs.
  • Variables: dashboard tương tác (chọn service, môi trường).

Ví dụ docker-compose Prometheus + Grafana

version: '3.8'
services:
  prometheus:
    image: prom/prometheus
    ports: ["9090:9090"]
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
  grafana:
    image: grafana/grafana
    ports: ["3000:3000"]
    environment:
      GF_SECURITY_ADMIN_PASSWORD: admin
# prometheus.yml
scrape_configs:
  - job_name: 'myapp'
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ['myapp:8080']
6. AWS CloudWatch

CloudWatch là gì?

Dịch vụ monitoring của AWS — thu thập metrics, logs, events từ các dịch vụ AWS (EC2, Lambda, RDS, ECS...). (AWS's monitoring service — collects metrics, logs, and events from AWS services.)

📈 CloudWatch Metrics

CPU, NetworkIn/Out của EC2; Duration/Errors của Lambda; được lưu 15 tháng.

📜 CloudWatch Logs

Tập trung log từ EC2 (agent), Lambda, ECS — query bằng Logs Insights.

🚨 CloudWatch Alarms

Rule theo threshold (CPU > 80% trong 5 phút) → trigger SNS → email/Slack.

📊 CloudWatch Dashboards

Gom metrics nhiều service vào 1 màn hình theo dõi.

Ví dụ alarm (Example)

# Alarms: CPU EC2 > 80% trong 5 phút
aws cloudwatch put-metric-alarm \
  --alarm-name high-cpu \
  --metric-name CPUUtilization \
  --namespace AWS/EC2 \
  --statistic Average \
  --period 300 \
  --threshold 80 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 2 \
  --alarm-actions arn:aws:sns:...:my-topic
7. Alerting & Incident

Alerting tốt (Good Alerting)

✅ Alert chuẩn

  • Dựa trên SLO — cảnh báo khi user bị ảnh hưởng
  • Hành động được — có runbook/người chịu trách nhiệm
  • Ít nhiễu — alert không rõ nguyên nhân = noise
  • Phân cấp: warning → critical → page (SMS/call)

❌ Tránh

  • Cảnh báo ồn ào (alert fatigue) — nhân viên bỏ qua
  • Threshold tùy tiện không gắn với user experience
  • Không có runbook — alert xong không biết làm gì

Ví dụ Prometheus alert rule

# alerting rule: 5xx rate > 1% trong 10 phút
groups:
  - name: app-alerts
    rules:
      - alert: HighErrorRate
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5.."}[10m]))
            / sum(rate(http_server_requests_seconds_count[10m])) > 0.01
        for: 10m
        labels: { severity: critical }
        annotations:
          summary: "Error rate > 1%"

Quy trình incident (Incident Flow)

Alert → Detect → Triage (mức độ) → Respond (runbook) → Mitigate → Postmortem (RCA)
8. Câu hỏi phỏng vấn (Interview Questions)

❓ Monitoring vs Observability?

Monitoring: detect vấn đề đã biết qua threshold. Observability: hiểu hệ thống qua metrics/logs/traces để debug vấn đề chưa biết.

❓ 3 trụ cột observability?

Metrics (số liệu theo thời gian), Logs (sự kiện chi tiết), Traces (hành trình request qua services).

❓ 4 golden signals?

Latency, Traffic, Errors, Saturation — của Google SRE để đo health hệ thống.

❓ Tại sao p95/p99 quan trọng hơn average?

Average che giấu các request chậm hiếm gặp; p95/p99 cho thấy trải nghiệm user ở đuôi phân phối — nơi dễ gây mất user.

❓ Prometheus pull vs push?

Prometheus dùng pull (scrape) — dễ discovery, tự kiểm soát tần suất. Push (Graphite/CloudWatch agent) phù hợp job ngắn hạn, firewall chặt.

❓ Distributed tracing để làm gì?

Gắn trace_id xuyên request qua nhiều services — tìm bottleneck, xem đúng service nào lỗi/chậm.
