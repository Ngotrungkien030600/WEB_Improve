1. IaC & Terraform là gì?

Infrastructure as Code (IaC)

Quản lý hạ tầng (VMs, networks, databases) bằng code thay vì bấm tay trên console. Code được version hóa, review được, tái dùng được. (Managing infrastructure via code instead of clicking in consoles — versioned, reviewable, reusable.)

⚙️ Imperative (thủ tục)

Mô tả cách làm từng bước. VD: Ansible, shell scripts. "Tạo VM, cài nginx, mở port 80..."

📜 Declarative (khai báo)

Mô tả kết quả mong muốn. VD: Terraform, CloudFormation. "Tôi muốn 1 VM có nginx chạy port 80."

Vì sao chọn Terraform?

  • Multi-cloud: AWS, GCP, Azure, Kubernetes, Cloudflare... qua provider.
  • Declarative: bạn khai báo desired state, Terraform tính ra thay đổi cần làm.
  • State-aware: biết chính xác tài nguyên nào đang tồn tại, tránh tạo trùng.
  • Plan trước khi áp dụng: xem diff trước khi thay đổi thật.
2. HCL & Cấu trúc file

Cấu trúc cơ bản (Basic Structure)

File .tf dùng ngôn ngữ HCL (HashiCorp Configuration Language) — đọc như JSON nhưng thân thiện hơn.

# main.tf
terraform {
  required_version = ">= 1.5"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "ap-southeast-1"
}

resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"
  tags = {
    Name = "web-server"
  }
}

Các khối chính (Key Blocks)

terraform {}

Khai báo required version, providers, backend (nơi lưu state).

provider ""

Cấu hình cloud provider (region, credentials). Provider biết cách tạo/tài nguyên trên cloud đó.

resource "" ""

Một tài nguyên cụ thể (EC2, S3 bucket, RDS...). Lõi của Terraform.

data "" ""

Đọc thông tin tài nguyên đã tồn tại (không tạo mới) để dùng trong code.

variable / output

Input parameters và giá trị trả ra sau apply (IP, endpoint...).

module ""

Đóng gói nhiều resources thành đơn vị tái dùng.

Ví dụ thêm (More Examples)

# S3 bucket
resource "aws_s3_bucket" "data" {
  bucket = "my-app-data-2026"
}

# Security group cho phép HTTP
resource "aws_security_group" "web_sg" {
  name = "web-sg"
  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
3. Workflow: init → plan → apply

Vòng đời Terraform (Terraform Lifecycle)

terraform init → terraform plan → [review diff] → terraform apply → terraform destroy
[tải providers] [tính diff vs state] [thực thi] [xóa hạ tầng]

1. init

Tải providers, modules, thiết lập backend state. Chạy 1 lần mỗi project.

2. plan

Tính toán thay đổi (create/update/delete) từ code vs state. Không thay đổi gì thật — an toàn để review.

3. apply

Thực thi thay đổi đã plan. Yêu cầu xác nhận (trừ khi -auto-approve).

terraform init                 # 1. Chuẩn bị
terraform fmt                 # Format code chuẩn
terraform validate            # Kiểm tra syntax
terraform plan -out plan.tfplan   # 2. Xem kế hoạch
terraform apply plan.tfplan   # 3. Áp dụng đúng plan đã review
terraform show                # Xem trạng thái hiện tại
terraform destroy             # Xóa toàn bộ hạ tầng đã tạo

Lưu ý

  • Luôn review plan trước apply — nhất là dòng -/+ (destroy + recreate) vì có thể gây downtime.
  • Không bao giờ sửa tài nguyên bằng tay trên console — Terraform sẽ xem đó là drift và có thể ghi đè.
4. State & Remote State

State là gì?

Terraform state (file terraform.tfstate) ghi lại ánh xạ giữa code và tài nguyên thực tế (resource ID, attributes). Đây là "nguồn chân lý" cho việc tính diff. (The state file records the mapping between your code and real resources — the source of truth for computing diffs.)

Tại sao cần remote state?

  • Chia sẻ team: state local (máy cá nhân) → mỗi người có state khác nhau → xung đột.
  • Backup & an toàn: state chứa secret (password DB, keys) — nên lưu nơi an toàn.
  • Locking: backend hỗ trợ khóa — 2 người không apply cùng lúc.
# Backend S3 (state lưu trên AWS S3 + khóa qua DynamoDB)
terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "prod/network/terraform.tfstate"
    region         = "ap-southeast-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

State backends phổ biến

AWS S3 + DynamoDB

Phổ biến nhất cho team dùng AWS — S3 lưu file, DynamoDB làm lock.

GCS / Azure Storage

Tương tự trên GCP/Azure.

Terraform Cloud / HCP

Managed state + remote runs, dễ integration với VCS.

Lưu ý bảo mật

  • State có thể chứa secrets — đừng commit state local vào git.
  • Dùng sensitive = true cho variables/outputs nhạy cảm.
  • Bật encryption cho backend state (S3 server-side encryption).
5. Modules

Module là gì?

A self-contained package of Terraform config that takes inputs and returns outputs — dùng để đóng gói hạ tầng tái dùng được (VD: module VPC, module EC2 cluster). (A self-contained package of Terraform config with inputs/outputs — reusable infrastructure building blocks.)

# modules/vpc/main.tf — module VPC tái dùng
variable "name"   { type = string }
variable "cidr"   { type = string }
variable "azs"    { type = list(string) }

resource "aws_vpc" "this" {
  cidr_block = var.cidr
  tags = { Name = var.name }
}

output "vpc_id" { value = aws_vpc.this.id }
# Sử dụng module trong root config
module "vpc" {
  source = "./modules/vpc"
  name   = "main-vpc"
  cidr   = "10.0.0.0/16"
  azs    = ["ap-southeast-1a", "ap-southeast-1b"]
}

output "vpc_id" {
  value = module.vpc.vpc_id
}

Registry modules

Dùng module công cộng từ Terraform Registry (hashicorp/terraform-aws-modules) — tiết kiệm thời gian, đã được cộng đồng kiểm chứng. (Use public modules from the Terraform Registry — battle-tested, time-saving.)

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.0.0"
  name = "my-vpc"
  cidr = "10.0.0.0/16"
}
6. Variables & Outputs

Input Variables

Tham số hóa config — tránh hard-code, dễ tái dùng giữa các môi trường. (Parameterize config — avoid hard-coding, reuse across environments.)

# variables.tf
variable "environment" {
  description = "Environment name"
  type        = string
  default     = "dev"
}

variable "instance_type" {
  type    = string
  default = "t3.micro"
}

variable "tags" {
  type = map(string)
  default = {
    Owner = "team-devops"
  }
}

Cách truyền giá trị (How to Pass Values)

# 1. File terraform.tfvars (ưu tiên)
environment = "prod"
instance_type = "t3.large"

# 2. CLI flag
terraform apply -var="environment=prod" -var="instance_type=t3.large"

# 3. Biến môi trường
export TF_VAR_environment=prod

Outputs

Trả ra giá trị sau apply — IP, endpoint, ID để dùng trong CI/CD hoặc module khác. (Return values after apply — IPs, endpoints, IDs for CI/CD or other modules.)

output "instance_ip" {
  value       = aws_instance.web.public_ip
  description = "Public IP of the web instance"
  sensitive   = false
}

# Dùng trong CI/CD
# terraform output instance_ip
7. Best Practices

Quy tắc vàng (Golden Rules)

✅ Nên làm

  • Chia môi trường bằng workspaces hoặc thư mục riêng (dev/staging/prod)
  • Dùng remote state + locking cho team
  • Pin version provider rõ ràng
  • Chạy terraform plan trong CI và yêu cầu review
  • Đặt tags chuẩn cho mọi resource (Name, Environment, Owner)
  • Dùng terraform fmt + validate trước commit

❌ Tránh

  • Hard-code secrets trong file .tf
  • Commit state local chứa secret
  • Sửa tài nguyên bằng tay trên console (drift)
  • Apply trực tiếp lên prod mà không plan/review
  • Dùng latest cho provider version

Workspaces

Nhiều state riêng biệt trên cùng 1 config — tiện cho dev/staging/prod cùng code. (Separate states on the same config — handy for dev/staging/prod.)

terraform workspace new dev
terraform workspace new prod
terraform workspace select dev
terraform apply

Terraform trong CI/CD

# Ví dụ GitHub Actions workflow
terraform init
terraform validate
terraform plan -out=plan.tfplan
# ... review thủ công qua PR comment ...
terraform apply -auto-approve plan.tfplan
8. Câu hỏi phỏng vấn (Interview Questions)

❓ Terraform vs Ansible?

Terraform: IaC declarative, tập trung provisioning hạ tầng (multi-cloud). Ansible: cả provisioning lẫn configuration bên trong server (imperative-ish, agentless). Thường dùng kết hợp.

❓ State file là gì, vì sao quan trọng?

Ghi ánh xạ code→tài nguyên thực tế. Quan trọng để tính diff chính xác, tránh tạo trùng. Nên lưu remote (S3 + DynamoDB lock).

❓ plan vs apply?

plan chỉ tính toán và hiển thị thay đổi (an toàn); apply thực thi thay đổi thật lên cloud.

❓ Module dùng để làm gì?

Đóng gói hạ tầng tái dùng (VPC, cluster) với inputs/outputs — giảm trùng lặp, chuẩn hóa kiến trúc.

❓ Remote state lợi ích?

Chia sẻ team, backup, locking chống apply song song, tách biệt môi trường.

❓ Drift là gì?

Trạng thái thực tế lệch với state/code (do sửa tay trên console). Terraform plan sẽ hiện drift và có thể khôi phục về desired state.
