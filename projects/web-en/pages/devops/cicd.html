1. CI/CD là gì? (What is CI/CD?)

Khái niệm (Concept)

CI — Continuous Integration: Tự động merge code thường xuyên, build và test mỗi lần có thay đổi — phát hiện lỗi sớm. (Frequently merge code, build and test on every change — catch bugs early.)

CD — Continuous Delivery/Deployment: Tự động đưa artifact đã test đạt chuẩn ra môi trường production. Delivery = chờ người duyệt; Deployment = hoàn toàn tự động. (Automatically ship tested artifacts to production. Delivery = manual approval gate; Deployment = fully automated.)

Code commit → Build → Test → (Quality gate) → Build image → Deploy staging → Deploy prod
[CI]                   [CD]

Lợi ích (Benefits)

⚡ Phát hiện lỗi sớm

Build/test tự động mỗi commit — bug bị bắt ngay, không chờ đến production.

🚀 Release nhanh & đều

Pipeline chuẩn hóa — không còn "chạy trên máy tôi vẫn OK".

🔁 Rollback dễ dàng

Artifact đã version hóa — quay lại version cũ chỉ là 1 thao tác.

2. Pipeline & Stages

Các stage điển hình (Typical Stages)

1. Checkout

Lấy source code từ git.

2. Install deps

Cài dependencies (npm ci, mvn dependency:go-offline).

3. Lint & Format

Kiểm tra code style (ESLint, Checkstyle).

4. Test

Unit test + integration test + coverage.

5. Build & Package

Compile, đóng gói artifact (jar, dist).

6. Build image & Push

Docker build + push lên registry (ECR, GHCR).

7. Deploy staging

Triển khai môi trường test, chạy smoke tests.

8. Deploy production

Có thể qua approval gate hoặc tự động (canary).

Pipeline as Code

Pipeline nên được khai báo trong git (YAML) — version hóa, review được, dễ tái dùng. (Pipelines should be declared in git as YAML — versioned, reviewable, reusable.)

  • GitHub Actions: .github/workflows/*.yml
  • GitLab CI: .gitlab-ci.yml
  • Jenkins: Jenkinsfile (declarative)
  • CircleCI: .circleci/config.yml
3. GitHub Actions

Cấu trúc workflow

Workflow = file YAML trong .github/workflows/, gồm events (trigger), jobs (chạy song song), steps (lệnh trong job). (A workflow is a YAML file with events that trigger it, jobs that run in parallel, and steps inside each job.)

# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '17'
      - name: Build with Maven
        run: mvn -B package --no-transfer-progress
      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: app-jar
          path: target/*.jar

CI/CD hoàn chỉnh với Docker

Phạm vi ví dụ: đoạn dưới đây minh họa deploy container lên một máy chủ Linux qua SSH + Docker Compose. Nó phù hợp với VM/server tự quản lý; không phải template deploy cho Lambda hoặc ECS. Với Lambda/ECS cần đóng gói và cập nhật tài nguyên theo dịch vụ tương ứng — xem phần tiếp theo.

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_TOKEN }}
      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          push: true
          tags: myorg/myapp:${{ github.sha }}
      - name: Deploy to server
        run: ssh deploy@server "docker pull myorg/myapp:${{ github.sha }} && docker compose up -d"

Lưu ý

  • Secrets khai báo trong Settings → Secrets → dùng qua ${{ secrets.NAME }}.
  • Dùng needs: để tạo dependency giữa jobs.
  • Cache dependencies (actions/cache) để pipeline nhanh hơn.
4. Deploy một repo lên AWS: dev → staging → production

Hai loại template cần phân biệt

Pipeline template

Workflow như .github/workflows/deploy.yml mô tả trigger, build, test, approval và cách gọi lệnh deploy. Có thể tách phần dùng chung thành reusable workflow.

Infrastructure template (IaC)

template.yaml của AWS SAM/CloudFormation, CDK hoặc Terraform mô tả Lambda, ECS, IAM, API, network và alarm. Template khai báo hạ tầng mong muốn; pipeline triển khai template đó vào từng environment.

Không phải một template duy nhất cho tất cả. Pipeline template quyết định thứ tự công việc; IaC template định nghĩa tài nguyên cloud. Ứng dụng Lambda thường dùng SAM/CloudFormation; ECS có thể dùng CloudFormation/CDK/Terraform cùng task definition và service.

Luồng điển hình của một repository

Pull request → lint + unit/integration test + security scan
Merge main → build một lần → lưu artifact có version → deploy dev → smoke test → promote đúng artifact lên staging → approval → promote đúng artifact lên production → monitor / rollback
  1. Pull request: chạy kiểm tra, không cấp quyền deploy production cho mã chưa được merge.
  2. Build một lần: tạo ZIP/JAR cho Lambda hoặc Docker image cho ECS; gắn commit SHA và lưu ở S3/ECR. Ghi lại image digest hoặc artifact version.
  3. Deploy dev: dùng cùng artifact với cấu hình dev, chạy smoke/integration test trên môi trường thật.
  4. Promote staging rồi production: đổi cấu hình/stack/account đích, không build lại source thành artifact khác. Staging kiểm tra gần giống production; production có approval, health alarm và rollback.

Environment không nhất thiết là một nhánh Git. Thường là target riêng với account hoặc role, stack/service/function, cấu hình và secret riêng. Nên cô lập production bằng AWS account riêng nếu tổ chức cho phép; quyền pipeline chỉ vừa đủ deploy vào target được giao.

Repository layout mẫu

orders-service/
├── src/                         # application code
├── tests/
├── template.yaml                # SAM / CloudFormation infrastructure
├── samconfig.toml                # per-environment stack parameters
└── .github/workflows/
    ├── ci.yml                    # PR: verify only
    └── deploy.yml                # build once, deploy/promote

Ví dụ A — AWS Lambda bằng SAM template

template.yaml vừa mô tả Lambda vừa mô tả cách phát hành an toàn. Stage là cấu hình không bí mật; credential/secret lấy từ IAM, Secrets Manager hoặc Parameter Store theo quyền của function.

Transform: AWS::Serverless-2016-10-31
Parameters:
  Stage:
    Type: String
    AllowedValues: [dev, staging, prod]

Resources:
  OrdersFunction:
    Type: AWS::Serverless::Function
    Properties:
      CodeUri: src/
      Handler: app.handler
      Runtime: nodejs22.x
      Timeout: 15
      MemorySize: 512
      AutoPublishAlias: live
      DeploymentPreference:
        Type: Canary10Percent5Minutes
        Alarms:
          - !Ref FunctionErrorAlarm
      Environment:
        Variables:
          APP_STAGE: !Ref Stage
      Policies:
        - AWSLambdaBasicExecutionRole

  FunctionErrorAlarm:
    Type: AWS::CloudWatch::Alarm
    Properties:
      Namespace: AWS/Lambda
      MetricName: Errors
      Dimensions:
        - Name: FunctionName
          Value: !Ref OrdersFunction
        - Name: Resource
          Value: !Sub '${OrdersFunction}:live'
      Statistic: Sum
      Period: 60
      EvaluationPeriods: 1
      Threshold: 1
      ComparisonOperator: GreaterThanOrEqualToThreshold
      TreatMissingData: notBreaching

Deploy lần đầu: SAM gradual rollout cần version Lambda cũ để so traffic. Ở stack mới, trước tiên deploy function với AutoPublishAlias nhưng chưa thêm DeploymentPreference; sau khi alias/version đã tồn tại, thêm canary preference và deploy lại. Các lần cập nhật tiếp theo mới shift traffic từ version cũ sang mới.

AutoPublishAlias tạo version/alias để chuyển traffic; DeploymentPreference yêu cầu SAM cấu hình gradual deployment qua CodeDeploy. Alarm lỗi có thể kích hoạt rollback. Chỉ thêm IAM policy đúng tài nguyên function cần truy cập, không cấp quyền rộng chỉ để pipeline chạy được.

Cấu hình target bằng samconfig.toml

[dev.deploy.parameters]
stack_name = "orders-dev"
region = "ap-southeast-1"
capabilities = "CAPABILITY_IAM"
resolve_s3 = true
parameter_overrides = "Stage=dev"

[staging.deploy.parameters]
stack_name = "orders-staging"
region = "ap-southeast-1"
capabilities = "CAPABILITY_IAM"
resolve_s3 = true
parameter_overrides = "Stage=staging"

[prod.deploy.parameters]
stack_name = "orders-prod"
region = "ap-southeast-1"
capabilities = "CAPABILITY_IAM"
resolve_s3 = true
parameter_overrides = "Stage=prod"
# Local/manual flow: build once, then select the target config
sam build
sam deploy --config-env dev
sam deploy --config-env staging
sam deploy --config-env prod

Trong CI, các lệnh promote phải nhận đúng build artifact đã tạo trước đó; không chạy lại build riêng ở staging/prod. Tài khoản AWS đích được quyết định bởi role/credentials mà job assume, còn --config-env chọn stack và parameter tương ứng.

GitHub Actions vào AWS: dùng OIDC thay access key dài hạn

Thiết lập GitHub OIDC provider và IAM role trust đúng repository/environment. Job chỉ xin token tạm thời; scope IAM role giới hạn theo account và tài nguyên cần deploy. Không lưu AWS access key dài hạn trong GitHub Secrets.

permissions:
  contents: read
  id-token: write

jobs:
  deploy-dev:
    runs-on: ubuntu-latest
    environment: dev
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v6.3.0
        with:
          role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}
          aws-region: ap-southeast-1
      - run: sam deploy --config-env dev --no-confirm-changeset

Workflow hoàn chỉnh cần thêm job CI/build, lưu và tải lại artifact, smoke test, dependency needs, cùng GitHub Environment protection cho staging/production. Environment có thể yêu cầu reviewer duyệt trước khi job production được cấp quyền chạy.

Ví dụ B — ECS: image → task definition → service

  1. CI build container một lần, push lên ECR với tag commit SHA; lấy image digest bất biến để biết chính xác revision nào đang promote.
  2. Task definition template trỏ tới image URI/digest, task role, execution role, port, resource limits và secret reference. Các giá trị theo environment như cluster, service, desired count và secret ARN được truyền lúc deploy.
  3. Đăng ký task definition revision mới, cập nhật ECS service ở dev và đợi service ổn định; chạy smoke test. Sau đó dùng cùng image digest để cập nhật staging và production.
  4. Rolling deployment phù hợp cách triển khai đơn giản. Khi cần blue/green hoặc traffic shift, cấu hình deployment controller/CodeDeploy, load balancer và health alarm; với CodeDeploy ECS thường cần hai target groups để giữ task set cũ và task set mới trong lúc chuyển traffic.
# Conceptual ECS release steps (the image is built once in CI)
docker build -t "$ECR_URI:$GIT_SHA" .
docker push "$ECR_URI:$GIT_SHA"
# Resolve and record the pushed image digest; render task definition with that digest.
aws ecs register-task-definition --cli-input-json file://rendered-task-definition.json
aws ecs update-service --cluster "$ECS_CLUSTER" --service "$ECS_SERVICE" --task-definition "$TASK_DEFINITION_ARN"
aws ecs wait services-stable --cluster "$ECS_CLUSTER" --services "$ECS_SERVICE"

Đoạn lệnh trên là khung luồng, cần điền registry, cluster, service, IAM role và file task definition của dự án. Nếu dùng ECS CodeDeploy blue/green, pipeline cần tạo deployment revision/AppSpec và cấu hình hai target groups, listener, alarm và rollback; không chỉ gọi update-service.

Checklist trước production

  • PR đã qua test, lint, scan dependency/image và review của người.
  • Artifact có commit SHA/version/digest; biết rõ artifact nào đang chạy ở dev, staging và production.
  • Mỗi environment dùng role, config, secrets, stack/service riêng; secret không nằm trong Git hay template plaintext.
  • Staging smoke test đạt; production có approval, health alarm, rollback plan và người theo dõi sau deploy.
  • Database migration tương thích ngược: ưu tiên expand → deploy code → migrate/backfill → contract sau; không phát hành code mới buộc mọi instance cũ dừng ngay lập tức.

Tự luyện theo repo mẫu

  1. Tạo function Lambda và SAM template cho dev; deploy bằng sam deploy --guided, sau đó đưa lựa chọn ổn định vào samconfig.toml.
  2. Tạo CI chạy test/build khi mở PR. Merge vào main chỉ tự deploy dev; staging chạy sau smoke test; production phải qua approval.
  3. Đối chiếu commit SHA và artifact version ở cả ba môi trường; chứng minh staging/prod đang dùng đúng artifact đã test.
  4. Thực hành cố ý làm health check fail ở dev/staging, đọc log, rollback và ghi lại cách xác nhận service đã ổn định.

Câu phỏng vấn: “How do you promote a change from development to production?”

Câu trả lời gợi ý: “I run the checks on the pull request, build an immutable artifact once, and deploy it to development first. After smoke tests pass, I promote the same artifact to staging and then to production through an approval gate. Each environment uses separate configuration and a least-privilege AWS role. I monitor health alarms after deployment and roll back if the release is unhealthy.”

Nghĩa: Tôi chạy kiểm tra trên pull request, build artifact bất biến một lần rồi deploy lên dev. Sau khi smoke test đạt, tôi promote chính artifact đó lên staging rồi production qua bước duyệt. Mỗi môi trường dùng cấu hình riêng và AWS role quyền tối thiểu. Sau deploy tôi theo dõi health alarm và rollback nếu bản phát hành không ổn định.

Tài liệu chính thức để đọc tiếp

  • AWS SAM: khai báo serverless resources và cấu hình nhiều environment trong samconfig.toml.
  • AWS SAM: gradual Lambda deployments và rollback.
  • ECS rolling deployments và ECS blue/green deployments.
  • GitHub Actions: kết nối AWS bằng OIDC.
5. Jenkins

Jenkins là gì?

Một CI/CD server tự-host truyền thống — cực kỳ linh hoạt nhờ hệ thống plugin khổng lồ. (A traditional self-hosted CI/CD server — extremely flexible thanks to a huge plugin ecosystem.)

Jenkinsfile (Declarative)

pipeline {
    agent any
    stages {
        stage('Checkout') {
            steps { checkout scm }
        }
        stage('Build') {
            steps { sh 'mvn -B package -DskipTests' }
        }
        stage('Test') {
            steps { sh 'mvn test' }
        }
        stage('Deploy') {
            steps { sh './deploy.sh' }
        }
    }
    post {
        success { echo 'Build succeeded!' }
        failure { echo 'Build failed!' }
    }
}

6. Deploy Strategies (Chiến lược triển khai)

🔄 Rolling Deploy

Thay từng instance cũ bằng mới dần dần — không downtime nhưng trong lúc đó có 2 version song song.

🔵🔵 Blue/Green

2 môi trường giống hệt (blue = cũ, green = mới). Deploy green, test xong chuyển traffic sang green. Rollback = chuyển ngược lại. Zero downtime, nhưng tốn gấp đôi tài nguyên.

🟡 Canary

Chuyển 5–10% traffic sang version mới trước, theo dõi metrics, rồi tăng dần lên 100%. Rủi ro thấp nhất.

🌊 A/B Testing

2 version khác nhau về tính năng, so sánh theo business metrics — thường không phải vì lý do kỹ thuật.

So sánh nhanh (Quick Comparison)

StrategyDowntimeRollbackChi phí tài nguyên
RollingKhông (tạm 2 version)Trung bình+1
Blue/GreenKhôngNhanh (chuyển traffic)x2
CanaryKhôngNhanh (tắt canary)+nhỏ (1 version mới)
7. GitOps & ArgoCD

GitOps là gì?

Git là single source of truth cho cả code lẫn cấu hình hạ tầng. Mọi thay đổi = pull request → merge → một operator tự động đồng bộ lên cluster. (Git is the single source of truth for both code and infrastructure config. Every change is a PR; an operator auto-syncs it to the cluster.)

Dev push code → Git repo (app + manifests) → ArgoCD detects change → Sync → Cluster state matches git

Lợi ích (Benefits)

  • Auditable: mọi thay đổi đều có PR + lịch sử git.
  • Rollback: revert commit là revert deploy.
  • Consistent: cluster luôn khớp với git (self-healing).

Công cụ (Tools)

ArgoCD

GitOps controller cho Kubernetes — sync manifests từ git, UI web, hỗ trợ multi-cluster, rollback tự động.

Flux CD

Alternate GitOps tool — family gồm kustomize-controller, helm-controller, image automation.

8. Quality Gates

Quality Gate là gì?

Ngưỡng chất lượng bắt buộc — pipeline fail nếu không đạt, ngăn artifact xấu lên production. (Mandatory quality thresholds — the pipeline fails if not met, blocking bad artifacts from reaching production.)

✅ Test coverage

VD: coverage ≥ 80% (Jacoco, Istanbul). Dưới ngưỡng → fail.

🔍 Static analysis

SonarQube — bug, code smell, security hotspot, duplications.

🔒 Security scan

SAST (Semgrep, Snyk), dependency check (OWASP), container scan (Trivy).

⚡ Performance check

Load test (k6, JMeter) — ngưỡng latency/error rate.

# Ví dụ: chặn build nếu coverage thấp (Maven + Jacoco)
mvn verify jacoco:check \
  -Djacoco.minimum=0.8 \
  -Djacoco.haltOnFailure=true
9. Câu hỏi phỏng vấn (Interview Questions)

❓ CI vs CD?

CI: build + test tự động mỗi commit. CD: tự động đưa artifact đạt chuẩn lên môi trường (Delivery = chờ duyệt, Deployment = tự động).

❓ Blue/Green vs Canary?

Blue/Green: 2 môi trường, chuyển toàn bộ traffic. Canary: chuyển từng phần nhỏ traffic để giảm rủi ro — an toàn hơn.

❓ GitOps hoạt động thế nào?

Git là nguồn chân lý; ArgoCD/Flux theo dõi repo và tự đồng bộ cluster khớp với git; rollback = revert commit.

❓ Làm sao pipeline không "green on every push"?

Quality gates: coverage ngưỡng, SonarQube, security scan, test thật — không chỉ build thành công.

❓ Artifact versioning?

Tag bằng commit SHA hoặc semantic version — reproducible builds, dễ rollback và trace.

❓ Secrets trong pipeline?

Dùng secrets vault (GitHub Secrets, Vault) — không bao giờ commit secret thật vào pipeline file.
